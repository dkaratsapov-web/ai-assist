# Развёртывание стенда

Пошаговая инструкция для домена **ai-helper.pro**. От начала до работающего
стенда — около часа, из которых большая часть уходит на сборку образов.

> **Подойдёт любой сервер с Ubuntu и Docker.** Ниже описан Timeweb Cloud, но
> VPS у Beget, reg.ru или любого другого провайдера настраивается ровно так же:
> шаги 3–7 от площадки не зависят.
>
> **Обычный («виртуальный», shared) хостинг не подойдёт** — например, тарифы
> вида Host-0. Он рассчитан на сайты на PHP: WordPress, Битрикс. Здесь нужны
> Docker, своя база, очередь и фоновые процессы, а на общем хостинге нет ни
> прав администратора, ни возможности запускать собственные службы. Это не
> вопрос мощности тарифа — такой хостинг устроен иначе.

> **Это staging-стенд, а не production:** реальных рекламных кабинетов здесь
> нет, система работает на заглушках. Вход при этом настоящий — через Яндекс ID,
> с личной учётной записью у каждого. Общий пароль на прокси убран: по нему в
> журнале не было видно, кто именно что сделал.

---

## 1. Виртуальная машина

Выбран **Timeweb Cloud**. Берётся обычный облачный сервер (VPS), не виртуальный
хостинг — см. оговорку выше.

| Параметр        | Значение                     |
| --------------- | ---------------------------- |
| Образ           | Ubuntu 24.04 LTS             |
| Ядер / память   | 2 ядра, 4 ГБ                 |
| Диск            | 30–40 ГБ NVMe                |
| Публичный адрес | Нужен, желательно постоянный |
| SSH-ключ        | Ваш публичный ключ           |

**Почему 4 ГБ, а не 2.** Сборка фронтенда — самый прожорливый шаг установки: на
замерах пик доходил до 2 ГБ. Запущенный сервис в 2 ГБ помещается свободно, а вот
собрать себя на такой машине не может — Docker убивает сборку по нехватке
памяти. На 2 ГБ это лечится файлом подкачки, и `setup-server.sh` создаёт его
сам, но сборка идёт заметно дольше.

**Управляемая база не нужна.** PostgreSQL поднимается контейнером на этой же
машине и входит в её стоимость. Отдельный управляемый кластер стоит в разы
дороже и на этом этапе не даёт ничего.

**Хостинг российский — это важно.** Не из принципа: как только в системе
появятся лиды с телефонами, это персональные данные граждан РФ, и по 152-ФЗ их
положено хранить на серверах в России. Timeweb и Beget подходят.

Любой другой провайдер подойдёт так же: те же 2 ядра, 4 ГБ, Ubuntu 24.04 и
публичный адрес. Дальше всё одинаково.

**Firewall** — только 22, 80 и 443. Порты PostgreSQL и Redis наружу не
открываются: база не должна быть доступна из интернета (v0.3 §104), compose их
не публикует, а `setup-server.sh` закрывает остальное через ufw.

## 2. Домен

Домен и сервер — разные вещи: домен может быть зарегистрирован где угодно, а
указывать при этом на любой сервер.

В DNS для `ai-helper.pro` нужна A-запись на публичный адрес сервера. Отдельная
запись для API не нужна: и сайт, и API живут на одном домене, API — по пути
`/api`. Так исчезает CORS и не приходится выпускать второй сертификат.

Нужны две записи:

| Тип | Имя   | Значение      |
| --- | ----- | ------------- |
| A   | `@`   | адрес сервера |
| A   | `www` | адрес сервера |

**Если домен в reg.ru:** личный кабинет → «Домены» → `ai-helper.pro` →
управление зоной DNS. Там же нужно **удалить существующие A-записи**, если
домен был привязан к услуге хостинга: иначе он продолжит показывать старый
сайт. Название пунктов меню у регистраторов меняется — ориентируйтесь на смысл.

Дождитесь, пока имя начнёт резолвиться, — Caddy получает сертификат по домену,
и до появления DNS-записи это не сработает. Обычно это занимает от нескольких
минут до пары часов.

## 3. Установка одной командой

На чистом сервере всё делает `setup-server.sh`: ставит Docker, создаёт файл
подкачки, закрывает firewall, готовит `.env` со сгенерированным паролем базы и
собирает стенд.

```bash
ssh root@<адрес-сервера>

git clone https://github.com/dkaratsapov-web/ai-assist.git
cd ai-assist
bash infra/setup-server.sh
```

Скрипт можно запускать повторно: всё уже сделанное пропускается. Это не
вежливость, а необходимость — на медленной машине установка занимает минуты и
вполне может оборваться на середине.

По окончании он печатает адрес сервера и что осталось сделать.

## 4. Конфигурация

`setup-server.sh` уже создал `infra/.env` и сгенерировал пароль базы. Остальное
заполняется руками:

- `YANDEX_OAUTH_CLIENT_ID` и `YANDEX_OAUTH_CLIENT_SECRET` — из приложения,
  зарегистрированного на <https://oauth.yandex.ru/client/new>. Адрес возврата в
  приложении: `https://ai-helper.pro/api/v1/auth/callback`, право — «Доступ к
  адресу электронной почты».
- `BOOTSTRAP_OWNER_EMAIL` — ваша почта в Яндексе. Первый вход с неё создаёт
  владельца, дальше эта дверь закрывается сама.

### 4а. Внешние сервисы

Всё, что ниже, необязательно: без этих строк система работает и честно
говорит, чего у неё нет. Добавляются по мере появления доступов.

**Модель.** Без ключа работает детерминированная заглушка: она отвечает по
схеме и ничего не стоит, но её ответы — не выводы модели, и выдавать их за
разбор нельзя. Поэтому там, где разбор моделью не подключён, система пишет об
этом прямо, а не показывает пустое место.

```
AI_PROVIDER=openai
OPENAI_API_KEY=<ключ>
```

Идентификатор модели меняется отдельными строками — код при этом не трогается:

```
OPENAI_MODEL=gpt-5.6-terra        # разбор сайта, конкуренты, рекомендации
OPENAI_MODEL_BULK=gpt-5.6-luna    # пачками: запросы, кластеры, объявления
```

`AI_PROVIDER=openai` без ключа роняет запуск намеренно. Молчаливый откат на
заглушку означал бы, что система продолжает работать, выдавая её выдумки за
разбор модели, и заметить подмену было бы нечем.

**Вордстат.** Отдельное приложение с правом `wordstat:api` и каталог Яндекс
Облака, в котором выданы права. Квота площадки — сто запросов в час на весь
сервис, поэтому сбор идёт заданием, а не кнопкой.

```
WORDSTAT_PROVIDER=yandex
YANDEX_WORDSTAT_TOKEN=<токен>
YANDEX_CLOUD_FOLDER_ID=<каталог>
```

**Директ и Метрика.** Токены можно положить заранее — работать система с ними
всё равно не начнёт: адаптер остаётся заглушкой до прохождения проверок
безопасности (см. 5а).

```
YANDEX_DIRECT_TOKEN=<токен>
YANDEX_DIRECT_LOGIN=<логин главного аккаунта>
YANDEX_METRICA_TOKEN=<токен>
```

После правки `.env` нужен перезапуск: файл читается при старте контейнера, и
без него всё останется по-старому.

```bash
cd ~/ai-assist/infra
docker compose --env-file .env up -d
```

Проверить, что значения доехали, — двумя командами. Первая про API, вторая про
воркер: разбор сайта и определение вида конкурента выполняются именно в нём, и
одного API здесь недостаточно.

```bash
curl -s https://ai-helper.pro/api/v1/health
docker compose exec worker printenv AI_PROVIDER WORDSTAT_PROVIDER
```

## 5. Первый запуск

```bash
cd ~/ai-assist/infra
docker compose --env-file .env up -d --build
```

Сборка занимает 5–15 минут.

Готово: откройте `https://ai-helper.pro` и нажмите «Войти через Яндекс».
Первый вход с почты из `BOOTSTRAP_OWNER_EMAIL` создаст вашу учётную запись с
ролью владельца. Остальных участников добавите на экране «Настройки».

## 5а. Проверка готовности

```bash
bash ~/ai-assist/infra/preflight.sh
```

Проверяет то, что нельзя увидеть глазами и о чём вспоминают после аварии: не
смотрят ли база и очередь в интернет, есть ли у краулера путь к базе, не попали
ли секреты в git, уводит ли HTTP на HTTPS, делаются ли резервные копии.

**Пока проверка не проходит, `AD_PLATFORM_LIVE_APPROVED` включать нельзя.** Это
не формальность: до тех пор система работает с чужими рекламными бюджетами
только понарошку, и цена ошибки равна нулю. После — не равна.

## 6. Проверка

```bash
docker compose ps                      # все сервисы healthy
docker compose logs -f api             # структурированные логи
curl https://ai-helper.pro/api/v1/health
```

Ответ `health` показывает режим работы: `ai_provider: stub` и
`ad_platform_adapter: mock` означают, что стенд работает на заглушках и
результаты не являются выводами настоящей модели.

Изоляция краулера проверяется одной командой — она должна **не** дать соединения:

```bash
docker compose exec crawler-worker python -c \
  "import socket; socket.create_connection(('postgres', 5432), timeout=3)"
```

Ожидаемый результат — ошибка разрешения имени. Если соединение установилось,
изоляция сломана: воркер, который ходит по чужим сайтам, получил доступ к данным
всех клиентов (v0.3 §97).

## 7. Резервные копии

Копии снимаются сами: контейнер `backup` делает дамп при старте и дальше раз в
сутки, складывает в `infra/backups/` и хранит последние 14. Число меняется
переменной `BACKUP_KEEP`.

Первая копия снимается сразу при развёртывании специально: неработающий бэкап
должен обнаружиться в тот же день, а не через сутки. Молча сломанный бэкап хуже
отсутствующего — на него рассчитывают.

**Проверить, что копии есть:**

```bash
ls -la backups/
```

**Восстановить** (данные текущей базы будут заменены):

```bash
docker compose stop api worker beat crawler-worker web
gunzip -c backups/ads_os_2026-08-15_03-00.sql.gz \
  | docker compose exec -T postgres psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"
docker compose start api worker beat crawler-worker web
```

**Перенести на другую машину** — обычным `scp`, копии лежат каталогом, а не в
томе Docker именно для этого:

```bash
scp -r backups/ user@новый-сервер:~/ai-assist/infra/
```

## 8. Переезд на другой хостинг

1. На старой машине снять свежую копию: `docker compose exec backup /usr/local/bin/backup.sh`
2. Скопировать `backups/` и `.env` на новую машину.
3. На новой развернуть по шагам 1–5 этого файла.
4. Восстановить базу командой из раздела выше.
5. Поменять A-запись домена на новый адрес.

Порядок важен: домен переключается последним, когда на новой машине уже всё
поднято. Иначе несколько минут сервис будет отвечать пустой базой.

## 9. Обновление

```bash
git pull
docker compose --env-file .env up -d --build
```

Миграции применяются отдельным сервисом до старта API: он не поднимется, пока
схема не обновлена.

## Состав сервисов

| Сервис           | Что делает                     | Видит базу | Ходит наружу |
| ---------------- | ------------------------------ | ---------- | ------------ |
| `caddy`          | TLS и маршрутизация            | нет        | да           |
| `web`            | Интерфейс                      | нет        | нет          |
| `api`            | HTTP API                       | да         | нет          |
| `worker`         | Разбор результатов, запись     | да         | нет          |
| `crawler-worker` | Загрузка чужих страниц         | **нет**    | да           |
| `migrate`        | Миграции схемы, разовый запуск | да         | нет          |
| `postgres`       | База                           | —          | нет          |
| `redis`          | Очередь задач                  | —          | нет          |

Строка `crawler-worker` — главная. Всё остальное в этой таблице описание, а она
требование: процесс, который разбирает произвольную внешнюю страницу, не должен
иметь возможности дотянуться до данных клиентов.

## Что осознанно не сделано

Это стенд, а не боевая инфраструктура. Ниже — то, что появится к MVP 2, когда
подключатся реальные рекламные кабинеты, и почему пока не нужно.

**Резервные копии.** Данных, которые жалко потерять, на стенде нет: всё
демонстрационное и восстанавливается скриптом. Требования по RPO/RTO из
v0.4 §14 относятся к боевому контуру.

**Раздельные окружения dev/staging/prod** (v0.3 §108). Пока контур один — их
незачем разделять. К моменту первого production-токена это обязательно.

**Секреты в Secret Manager.** Сейчас они в `.env` на сервере. Для стенда без
реальных токенов это приемлемо; как только появится OAuth-токен рекламного
кабинета — обязателен Yandex Lockbox или KMS, потому что токен даёт доступ к
чужим бюджетам (v0.3 §94).

**Сборка образов в CI и реестр.** Сейчас образы собираются на самой машине.
Это проще и не требует настройки Container Registry, но занимает ресурсы ВМ во
время сборки. При переходе на несколько окружений — вынести в CI.

**Ограничение исходящего трафика воркера краулера на уровне облака.** В compose
краулер уже отрезан от базы: он состоит только в сети `crawler`, где базы нет, и
адрес базы ему не передаётся. Чего compose не даёт — ограничения того, куда
краулер может ходить наружу. Это делается группой безопасности Яндекс Облака или
NAT-шлюзом с белым списком; до этого остаётся риск, описанный в
`services/crawler/ssrf.py`.
