# ADS OS — зафиксированные решения v0.4

Документ создан по требованию `ADS OS v0.4 Architecture Hardening Addendum §24`.

Назначение: собрать в одном месте решения, которые больше не обсуждаются при
реализации, и отдельно — допущения, принятые за отсутствием решения владельца
продукта. Второе помечено `⏳ требует подтверждения` и подлежит явному
подтверждению до того, как на нём вырастет значимый объём кода.

## Порядок приоритета документов

При конфликте выигрывает документ выше по списку (v0.4 §26):

1. ADS OS v0.4 Architecture Hardening Addendum

## 2. Канонический жизненный цикл проекта — закрыто

Разрозненные 8/10/12-шаговые представления из v0.3 заменены единым lifecycle
(v0.4 §3):

```
1. Onboarding   →  2. Research   →  3. Economics  →  4. Strategy  →  5. Build
6. Validate     →  7. Launch     →  8. Measure    →  9. Optimize  → 10. Experiment & Scale
```

Маппинг модулей:

```
Research  ├── Website Audit        Build     ├── Semantics
          └── Competitors                    ├── Clustering
                                             ├── Structure
Measure   ├── Metrica                        ├── Ads
          ├── CRM                            └── Creatives
          ├── Calltracking
          └── Tracking Health      Optimize  ├── Search Queries
                                             ├── Budget Pacing
                                             ├── Landing Optimizer
                                             └── Lead Quality
```

Backend-статусы остаются техническими и **не обязаны** совпадать 1:1 с UX-lifecycle.

> **Следствие для UI.** Референс 3 (Web dashboard) рисует цепочку из 8 шагов.
> Канонический lifecycle — 10 шагов, и по правилу приоритета он выигрывает.
> `WorkflowStepper` реализован на 10 позиций с горизонтальным скроллом.

## 4. Autopilot — закрыто

Все автопилот-действия по умолчанию **выключены** (v0.4 §10). Примеры из v0.3 §55,
где что-либо включено по умолчанию, недействительны.

```
autopilot_enabled     = false
negative_keywords     = approval
pause_keyword         = approval
budget_reallocation   = approval
new_campaign          = off
geography_change      = off
```

«Достаточность данных» — только action-specific через `PolicyThreshold`
(`minimum_clicks`, `minimum_spend`, `minimum_conversions`, `minimum_days`,
`minimum_confidence`, `tracking_health_required`, `attribution_health_required`,
`freshness_limit`, `max_change_percent`). Единый порог на все действия запрещён.

## 5. Экономика и Limited Economics Mode — закрыто

AI-бриф не изображает, что может получить внутреннюю экономику с сайта (v0.4 §5).

| Категория | Поля |
| --- | --- |
| Auto-discovered | услуги, товары, публичные цены, география, CTA, УТП, акции |
| Required business input | `monthly_budget`, `average_order_value` OR `expected_value`, `main_conversion` |
| Recommended business input | `margin_percent`, `lead_to_sale_rate`, `target_CAC`, `target_CPL` |

Без recommended-полей проект **не блокируется**: Economics Health помечается как
`incomplete`, рекомендации по марже и CAC не выдаются как достоверные, в качестве
временных proxy-метрик используются CPL и конверсии, в интерфейсе показывается CTA
«Заполнить экономику, чтобы включить оптимизацию по продажам».

## 6. Forecast — закрыто

Уровни зрелости (v0.4 §6): Level 0 Cold Start → Level 1 Project Learned →
Level 2 ADS OS Benchmark.

Обязательные поля прогноза: `forecast_source` (platform | project_history |
benchmark | heuristic | mixed), `confidence` (low | medium | high),
`assumptions[]`, `generated_at`, `valid_until`.

Прогноз без диапазона и confidence не показывается никогда.

## 7. Attribution Layer — закрыто

Все метрики продаж и CAC считаются только через явно выбранную модель атрибуции
(v0.4 §7). `AttributionConfig` версионируется, смена модели требует approval,
отчёты сохраняют `attribution_version`. Смешивать продажи из разных attribution
rules внутри одного KPI без явной маркировки запрещено.

## 8. Source of Truth — закрыто

| Метрика / сущность | Источник правды |
| --- | --- |
| Spend, Impressions, Clicks, Search Queries | Ad Platform |
| Visits, Web Conversions | Metrica |
| Lead Created, Lead Status, Qualified Lead, Sale | CRM |
| Revenue | CRM / ERP |
| Project Budget Limit, Autopilot Policy | ADS OS |
| Competitor Observation | ADS OS Evidence Store |

При расхождении источников система не выбирает число молча — расхождение
фиксируется вместе с источником (v0.4 §8).

## 9. Data Freshness — закрыто

Целевая свежесть (v0.4 §9): spend/clicks 15–60 мин · состояние кампаний 5–15 мин ·
поисковые запросы 1–6 ч · конверсии Метрики 15–60 мин · лиды CRM < 5 мин ·
qualified/revenue — событийно · сайты конкурентов 3–14 дней · benchmarks — ежедневно ·
forecast — до истечения assumptions.

Policy Engine учитывает свежесть: финансовое действие не выполняется на данных
старше допустимого TTL.

## 10. Нагрузочные ориентиры и БД — закрыто

Design targets (v0.4 §12): 100 организаций · 1 000 пользователей · 2 000 проектов ·
50 000 кампаний · 10–20 млн ключей · 100+ млн строк search-query в год ·
200 одновременных пользователей · 1 000+ фоновых заданий в час.

Требования: статистические и search-query таблицы partition-ready с первой
миграции, партиционирование по дате, индексы под `project_id + date + campaign_id`,
raw events отделены от агрегатов, analytics repository изолирован для возможного
выноса. ClickHouse в MVP не используется.

## 11. Metering — закрыто

Учёт потребления обязателен с первого дня, платёжная система в MVP не нужна
(v0.4 §13). `UsageEvent` создаётся на каждый LLM-вызов; считаются страницы
краулера и вызовы платных внешних API. `OrganizationPlan` хранит лимиты.

## 12. SLA / RPO / RTO — закрыто

Внутренние engineering targets, не публичный SLA (v0.4 §14): доступность 99.5%,
RPO ≤ 24 ч для MVP (цель ≤ 1 ч до зрелого production), RTO ≤ 4 ч,
подтверждение критического security-инцидента ≤ 1 ч, kill switch внешних действий —
немедленный, вручную из Owner control plane.

## 13. Роадмап — закрыто

`MVP 0 Core` → `MVP 0.5 Research` → `MVP 1 Campaign Draft` →
`MVP 2 Live Ads + Measurement` → `MVP 2.5 Business Feedback` →
`MVP 3 Optimization` → `MVP 4+` (v0.4 §15).

## 14. Процесс и инструменты — закрыто

- **Module spec** (v0.4 §21): перед модулем — один короткий `module-spec.md` на
  1–2 страницы по 10 пунктам (Purpose, Input, Output, Data Model, External APIs,
  Side Effects, Failure/Retry, Permissions/Security, Audit Events, Tests).
  Тяжёлая процедура из v0.3 §73 не применяется.
- **Storybook** (v0.4 §22): только базовая библиотека компонентов (~20 штук),
  не страницы. Страницы проверяются на demo-проекте в приложении.
- **i18n** (v0.4 §23): первый релиз только `ru-RU`, фреймворк локализации не
  подключается. Пользовательские бизнес-данные при этом не зашиваются в UI-labels.
- **Design tokens** (v0.4 §19): единый `design-tokens.json` →
  CSS variables → Tailwind theme → Web-компоненты → константы сообщений ботов.
- **Краулер** (v0.4 §20): изоляция сети с первого окружения, SSRF-контроль до
  первого реального URL.

## Допущения, принятые за отсутствием решения

Все помечены `⏳ требует подтверждения`. Каждое можно отменить дешёво, пока на нём
не выросла реализация; точка невозврата указана отдельно.

### A. Каналы Telegram / MAX в роадмапе ⏳

Роадмап v0.4 §15 не называет этап, на котором появляются боты, хотя v0.4 §2.5
объявляет Telegram первым production-мессенджером.

**Принято:** `ChannelAdapter` + `ChannelIdentity` + `LinkToken` — в MVP 0
(интерфейс и модель, без самого бота). Бот-уведомления read-only — в MVP 3
вместе с Alerts. Полный assistant-бот с approvals — в MVP 4+. MAX — stub до
подтверждения зрелости его Bot API.
**Точка невозврата:** начало MVP 3.

### B. Limited Attribution Mode ⏳

Attribution Layer стоит в MVP 2, а CRM — в MVP 2.5. Значит на MVP 2 источника
для `sale` и `revenue` физически нет.

**Принято:** симметрично Limited Economics Mode. `AttributionConfig` получает
`conversion_source ∈ {metrica, crm}` и `revenue_source ∈ {none, crm}`. Пока
`revenue_source = none`, метрики CAC / ROAS / выручка помечаются недоступными и не
участвуют ни в одной рекомендации. Каждый KPI получает состояние
`available | proxy | unavailable`, зависящее от подключённых источников.
**Точка невозврата:** проектирование KPI-компонентов (наступила — состояние KPI
уже заложено в `KpiCard`).

### C. Определение Attribution Health ⏳

`PolicyThreshold` использует `attribution_health_required`, но само понятие в ТЗ
не описано (в отличие от Tracking Health в v0.3 §39).

**Принято:** `healthy | warning | critical` по признакам — доля лидов без
`yclid`/ClientID выше порога; лаг синхронизации CRM выше TTL из Freshness Matrix;
`attribution_version` менялась менее N дней назад; расхождение «лиды CRM ↔
конверсии Метрики» выше допуска. При `critical` блокируются действия, зависящие от
продаж и CAC.
**Точка невозврата:** реализация Policy Engine (MVP 3).

### D. Механизм фиксации расхождений ⏳

v0.4 §8 требует не выбирать число молча, но не задаёт ни сущности, ни допусков.

**Принято:** сущность `MetricDiscrepancy (project_id, metric, source_a, value_a,
source_b, value_b, delta_pct, detected_at, status)`. Сравниваемые пары и допуски
по умолчанию: клики Директа ↔ визиты Метрики ±15%; конверсии Метрики ↔ лиды CRM
±10%; spend сравнению не подлежит — единственный источник Ad Platform. Превышение
допуска даёт warning-бейдж на KPI и запись, но не алерт.
**Точка невозврата:** MVP 2 (появление второго источника данных).

### E. Свежесть как свойство данных ⏳

Чтобы правило v0.4 §9 работало, недостаточно проверки в Policy Engine.

**Принято:** аналитический репозиторий возвращает не голое число, а
`(value, as_of, source)`. Вводится `SyncState (project_id, source, data_type,
last_synced_at, status)`. Все аналитические ответы API несут `as_of` и `source`.
`FreshnessGuard` — отдельная проверка в Policy Engine рядом с Tracking Health.
**Точка невозврата:** проектирование ERD аналитики (MVP 2).

### F. Стратегия эмбеддингов ⏳

Целевые 10–20 млн ключей делают наивный подход невозможным: вектор на каждую
сырую фразу в 1536 измерениях — это порядка сотни гигабайт до индекса.

**Принято:** эмбеддинги считаются для **нормализованных дедуплицированных** фраз,
размерность 512–768 либо `halfvec`, индекс HNSW, векторы в отдельной таблице от
`Keyword`, кластеризация на уровне проекта, а не глобально.
**Точка невозврата:** MVP 1 (модуль кластеризации).

### G. Сроки хранения данных ⏳

v0.3 §110 требует определить сроки, цифры не заданы.

**Принято:** raw search-query строки — 13 месяцев, дальше только агрегаты
(кампания / кластер / неделя) бессрочно. Crawler snapshots — 90 дней.
AI payloads — 30 дней. Логи — 30 дней. Audit trail — бессрочно.
**Точка невозврата:** первая миграция аналитических таблиц (MVP 2).

### H. Область действия PolicyThreshold ⏳

v0.4 §10 перечисляет поля, но не задаёт scope и владельца.

**Принято:** три уровня — `global default` (в коде/сиде) → `organization override`
→ `project override`, разрешение сверху вниз. Редактирование только роль OWNER и
только через сайт, каждое изменение попадает в Audit Log. AI и autopilot не могут
менять пороги никогда.
**Точка невозврата:** MVP 3.

### I. Критерии приёмки качества AI ⏳

Definition of Done есть для кода (v0.3 §77) и для UI (v0.3 §150), но не для
качества AI-выходов. Без этого у MVP 1 нет условия завершения.

**Принято:** размеченный эталонный набор на demo-проекте (300–500 запросов с
ручной разметкой intent и кластеров), хранится в репозитории и прогоняется как
тест при смене промптов или модели. Пороги приёмки: intent accuracy ≥ 85%;
≥ 90% ключей распределены по осмысленным кластерам по оценке специалиста;
≥ 80% сгенерированных объявлений проходят предмодерацию без правок;
0 фактических утверждений о конкурентах без evidence.
**Точка невозврата:** начало MVP 1. Эталонный набор требует участия специалиста.

### J. Частичный сбой публикации в Директ ⏳

v0.3 §100 упоминает rollback для обратимых операций, но не описывает сверку при
частичном сбое (создались 10 групп из 50).

**Принято:** публикация — job с чекпоинтами по сущностям, `external_id`
записывается сразу после каждого успешного создания. При сбое кампания получает
статус `partially_published`, пользователю показывается экран сверки
«создано / не создано / расходится», повтор запускается только для недостающего.
**Точка невозврата:** MVP 2.

### K. WorkflowStepper на 10 шагов ⏳

Референс 3 рисует 8 шагов, канонический lifecycle — 10. По правилу приоритета
выигрывает lifecycle.

**Принято:** 10 позиций, компактные карточки, горизонтальный скролл, завершённые
шаги сворачиваются. Отступление от макета осознанное.
**Точка невозврата:** наступила — реализовано в текущем срезе.

### L. Разделение dev-провайдера и production-политики PII ⏳

Пункт `LLM provider policy for PII` из v0.4 §25 заблокировал бы MVP 0, если
трактовать его как единое решение.

**Принято:** решение разделено. Провайдер для разработки в режиме `SAFE_PUBLIC`
принят (YandexGPT, см. выше). Production-политика обработки `SENSITIVE`-данных
решается отдельно к MVP 2.5, когда появляются реальные лиды. До этого момента
`AI_SENSITIVE_PROVIDER=none`.
**Точка невозврата:** MVP 2.5.

## Дополнение к структуре проекта

v0.3 §72 задаёт `/packages/{shared,schemas,ui}`. Добавлен `packages/tokens`:
v0.4 §19 требует единого источника design-токенов, из которого генерируются и
CSS-переменные Web, и константы сообщений ботов. Держать этот источник внутри
`packages/ui` было бы неверно — потребители токенов шире, чем React-компоненты.
